## 四、已经做好的准备

### 1. 同步状态现在看得见了

**这是接数据库前最该补的一处。** 之前 `lib/sync.ts` 里所有错误都被 `.catch(() => {})`
吞掉——同步失败对用户完全不可见：书架只在本机、账户没更新，读者却毫不知情。

现在：

- `lib/sync.ts` 暴露 `SyncState`（`off` / `working` / `error`）与 `useSyncState()`
- 失败时底部出现提示条：「没有同步到你的账户。书架在这台设备上还是安全的。」+ 重试按钮
- 下次同步成功后提示条自动消失
- 日常阅读时不出现，不打扰

### 2. schema 与同步 SQL 已在本地的真 Postgres 上验证过

`npm run db:verify` 用 **PGlite**（真 Postgres 的 WASM 版，语义与 Neon 一致）跑完整流程，
15 项全过：

```
✅ 15 条语句执行完毕
✅ 8 张表：agent_tokens, articles, briefs, covers, free_usage, glosses, highlights, progress
✅ 15 个索引，含全部 6 个同步索引
✅ schema 可以重复执行（migrate 幂等）
✅ 文章写入：数据与正文都在
✅ 高亮写入正常
✅ 高亮更新（upsert 覆盖）正常
✅ 不带正文的更新：正文被保留（coalesce 生效）
✅ 删除走墓碑：deleted=true、正文清空
✅ pull（按 updated_at 取变更）正常
✅ 用户隔离：另一个用户看不到这些行
✅ free_usage（按金额计费）正常
✅ agent token 写入正常
✅ agent token 的 hash 唯一约束生效
✅ 封面写入正常
```

覆盖的关键点：**正文不会被空更新覆盖**（`coalesce(excluded.doc, articles.doc)`）、
**删除走墓碑而非物理删**（其他设备才知道）、**用户隔离**（`user_id` 过滤）。

### 3. 接到 Neon 后的体检脚本

`npm run db:check` 会逐项检查并给出结论：配置在不在、连不连得上、表齐不齐、
索引齐不齐、**写进去读得出来吗**（插一行再删掉）、`free_usage` 有没有 `usd` 列。
没配置时它直接打印三步指引。

**没有期限。** Neon 官方原话是 "$0/month, no time limits and no credit card required"

| 信用卡 | **不需要** | 不填卡也用 |

### 超额了会怎样（关键）

**不会扣钱。** Neon 官方明确："Neon does not bill overages on the Free plan."

- **计算用完**（100 CU-小时用尽）→ 该项目的计算**暂停**，等下个月自动恢复。
  连接会断，但**数据不丢**，也不产生任何费用。
- **存储超 1 GB** → 增删改**失败**（报错），直到你清出空间。
  ⚠️ 这是唯一会"卡住"你的地方，而且要清空间才能恢复。
- **分支超 10 个** → 建新分支失败，删掉一个就行。

**所有限制都不会删除你的数据。**

### 每月重置 vs 持续限制

- **计算时长、网络流量** → 每个账单周期开始时重置
- **存储、分支数、项目数** → 持续限制，不重置（所以存储要注意）

## 六、给很多人一起用，够不够

实测过（`npm run db:measure-traffic`、`npm run db:measure-http`、`npm run db:measure-query`）。

### 结论：几十人用 $0 没问题；上百人要把同步间隔调大

**流量是比存储紧得多的那条线。** 一次 pull 在网络上的完整往返（请求行、请求头、
状态行、响应头、JSON 全算）是 **205 字节** —— 比 JSON 响应体本身（0.11 KB）大得多。

Neon 免费版每个项目每月 5 GB 流量，于是：

**最坏情况**（所有人都一直开着书架页）：

| 同步间隔 | 每人每月 | 5GB 支撑 |
|---|---|---|
| 5 秒（现在的默认） | 101 MB | **51 人** |
| 15 秒 | 34 MB | 152 人 |
| **30 秒** | 17 MB | **303 人** |
| 60 秒 | 8.4 MB | 606 人 |
| 300 秒 | 1.7 MB | 3,031 人 |

**典型用法**（每人每天在书架页 30 分钟，其余时间在读文章）——这才是实际：

| 同步间隔 | 每人每月 | 5GB 支撑 |
|---|---|---|
| 5 秒 | 2.2 MB | **约 2,300 人** |
| 30 秒 | 0.5 MB | 约 10,900 人 |

差别这么大，是因为代码里已经有三重保护（`lib/sync.ts`）：
- 轮询**只在书架页**跑（`watchers` 才启动 ticker），读文章的页面只在切回前台时拉一次
- 标签页切到后台（`visibilityState === "hidden"`）**完全不拉**
- pull 是增量的（带 `since` 时间戳），只拉变化的部分，且**不拉正文**

**存储完全不是问题**：每人 216 KB（10 篇文章 + 50 高亮 + 30 批注），
1 GB 能装 **4,850 人**。

**计算也不是问题**：查询走索引（实测确认 `Bitmap Index Scan on articles_user_updated`），
50 用户 × 20 篇的量下，一次完整 pull（6 个查询）**3.3 ms**。
500 人同时开着书架页 ≈ 600 查询/秒，2 CU 扛得住。

### 所以：人多了先调间隔，别先升级

`NEXT_PUBLIC_SYNC_INTERVAL_MS` 就是干这个的（`lib/sync.ts` 的 `WATCH_MS`，
现在从环境变量读，默认仍是 5000）：

```bash
# .env.local
NEXT_PUBLIC_SYNC_INTERVAL_MS=30000
```

**间隔从 5 秒调到 30 秒，最坏情况下的支撑人数从 51 变成 303，流量降 6 倍，$0 不变。**

代价：agent 存进书架的东西，晚 30 秒才出现。对一个读书应用完全无所谓。

### 真正会先撞到的三道墙

1. **流量**（Neon 5GB/月）—— 最坏情况几十人，典型用法两千人
2. **Next.js 托管**（Vercel Hobby 的并发与函数数限制）—— 通常先于数据库成为瓶颈
3. **共享 Together key 的免费额度** —— `free_usage` 表里每人每天 $0.2，
   但全体上限 `$1000/天`，人多了这个先见底
4. Clerk 免费版 50,000 月活 —— 反而是最远的一道

### 阶段表

| 阶段 | 人数 | 怎么变 |
|---|---|---|
| 现在 | 1-50 | Neon Free + Clerk Free，**$0** |
| 小范围分享 | 50-300 | 仍是 Free，$0。**把 `NEXT_PUBLIC_SYNC_INTERVAL_MS` 调到 30000** |
| 认真做 | 300+ | Neon **Launch**（$0.106/CU-小时、$0.35/GB-月，无月费门槛） |

## 八、常见问题

**Neon 免费版会不会哪天收费？**
不会。官方明确免费层"no time limits"、不需信用卡，且 **"Neon does not bill overages
on the Free plan"** —— 超额只会暂停/拒绝写入，不会产生账单。

**怎么看自己用了多少？**
Neon Console 的 project 页面有 Storage 和 Compute 的用量条，
Billing 页面能看到当前计费周期的 CU-小时消耗。

**超了怎么办？**
- 计算用完 → 等下个月自动恢复，或者升级
- 存储超 1 GB → Console 里删掉一些数据腾空间（`npm run db:check` 会显示数据概况）
- 数据不会被删

**`npm run db:migrate` 报连接错误？**
检查连接串是不是完整复制了（Neon 面板上有个复制按钮）。连接串要带 `?sslmode=require`。

**表建了但同步还是 503？**
跑 `npm run db:check`，它会指出缺什么。改完 `.env.local` 要重启 dev server。

**同步提示一直显示？**
说明 `/api/sync` 一直失败。打开浏览器开发者工具看 Network 里 `/api/sync` 的响应，
`npm run db:check` 也会指出问题。

**不想用数据库？**
也行。应用在没有数据库时完全可用——只是数据留在本机，登录不带来跨设备同步。
删掉 `DATABASE_URL` 就回到那个状态。
