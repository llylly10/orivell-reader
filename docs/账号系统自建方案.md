# Gloss 账号系统自建方案

> 把 Clerk 换成自己实现的邮箱登录，并加上邮件推送。
> 面向单人使用（本人 + 少量朋友），保留跨设备同步与 MCP Agent 接入。
>
> 撰写日期：2026-10-20
> 适用版本：`gloss-upstream`，Next.js 16.4.0，commit `95373eb`（与上游 `Nutlope/gloss` 零差异）

---

## 一、先说结论

这件事**可以做，而且比想象的干净**，原因是一个架构特性：

> 整个账号系统只认`userId` 这一个字符串。

`db/schema.sql` 里 8 张表的主键全是 `user_id text`，服务端8 处`auth()` 全部只取 `.userId` 就丢给数据库。**没有用到 Clerk 的组织、团队、OAuth 设备管理、Webhook、后台界面。**

所以替换 Clerk 本质是换一个「拿到 userId 的函数」+一套登录界面，数据层一行都不用改。

### 工作量估算

| 阶段 | 内容 | 预估 |
|---|---|---|
| 0 | 接数据库（前置依赖） | 30 分钟 |
| 1 | 建表 + 认证核心 | 3 小时 |
| 2 | 登录界面 | 2-3 小时 |
| 3 | 替换 22 处耦合点 | 1 小时 |
| 4 | 邮件推送 | 2 小时 |
| 5 | 部署 | 1 小时 |

**总计约 1.5 天**，其中最耗时的是登录界面（这个项目对视觉要求高）。

## 二、方案选型：为什么不用现成的库

考虑过三个方案：

| 方案 | 判断 |
|---|---|
| Clerk（现状） | 免费层 1 万 MAU 够用，但登录页实测空白，且要长期依赖外部服务 |
| Better Auth | 功能完备，支持多种 OAuth。**但单人使用 overkill，且登录 UI 仍要自己画** |
| **自建（推荐）** | 单人使用下最简单，无依赖，完全可控，且是用户明确的学习目标 |

**决策依据**：项目已有完整的 `userId` 抽象，自建的边际成本比接一个新库更低。而且单人使用，不需要多 OAuth provider、不需要多租户、不需要 OAuth 设备管理——这些正是现成库的主要价值所在。

**保留的能力**：跨设备同步、MCP Agent 接入。**放弃的能力**：GitHub/Google 社交登录（单人使用不需要，以后想加再接）。

## 四、数据库设计

在 `db/schema.sql` 末尾追加两张表。原文件的风格是**全部 `create table if not exists`，可重复执行**——新表必须遵守。

```sql
-- Accounts for Gloss readers. One row per person; the id is what every other
-- table's user_id column points at, replacing Clerk's user ids.
-- Password hashes are scrypt with a per-user salt, never the password itself.
create table if not exists users (
  id text primary key,             -- "usr_" + 16 random bytes, base64url
  email text not null unique,      -- lowercased; the login name
  name text,
  hash text not null,              -- "scrypt$N$r$p$salt$derived", base64url parts
  created_at timestamptz not null default now(),
  last_seen_at timestamptz
);

-- Sessions: one row per signed-in browser. The cookie carries only the id;
-- the token is stored hashed, so a database leak does not hand over logins.
create table if not exists sessions (
  id text primary key,
  user_id text not null references users (id) on delete cascade,
  token_hash text not null unique, -- sha256 of the cookie value
  created_at timestamptz not null default now(),
  expires_at timestamptz not null, -- sliding: renewed on use, max 30 days
  user_agent text
);

create index if not exists sessions_user on sessions (user_id);
create index if not exists sessions_expiry on sessions (expires_at);
```

### 设计要点

**为什么 `user_id` 用 `text` 而不是 uuid**
保持与现有 8 张表一致，`agent_tokens.user_id`、`covers.user_id` 等都不需要改类型。

**为什么 Cookie 只存 id，数据库存 token 哈希**
数据库泄露时，攻击者拿到的是 `token_hash`，无法直接当Cookie 用。这是标准做法（Clerk、GitHub 都这么做）。

**为什么用滑动过期**
`expires_at` 在每次使用会话时续期，但设30 天上限。频繁使用就一直有效，30 天不用就自动失效。

**密码哈希参数**
`scrypt` 的标准参数（N=16384, r=8, p=1），约 100ms/次——对单人系统足够慢到抵抗暴力破解，又不至于让登录变卡。

## 五、认证核心实现

### 5.1 新建 `lib/auth.ts`

这是整个方案的核心。放在`lib/` 下，与 `db.ts`、`agent.ts` 同级。

```typescript
/**
 * Accounts: the reader signs in with an email and a password, and carries a
 * cookie that names a session. Everything else in Gloss only ever needs the
 * user's id, which is what the signed-in cookie resolves to.
 *
 * - Passwords are hashed with scrypt and a per-user salt. The hash is stored
 *   with its parameters, so an old cost can still be verified later.
 * - The cookie carries a random id. Only the hash of the cookie's token is
 *   kept, so a leaked database does not hand over live sessions.
 * - Sessions expire, and slide: each use renews the expiry, capped at 30 days.
 */

import { createHash, randomBytes, scryptSync, timingSafeEqual } from "node:crypto";
import { cookies } from "next/headers";
import { db } from "./db";

/** The cookie that carries the session id. Shared with lib/session.ts, which reads it. */
export const COOKIE = "gloss_session";
const SCRYPT = { N: 16384, r: 8, p: 1, keylen: 64 };

/* ---------- password hashing ---------- */

const enc = (b: Buffer) => b.toString("base64url");

/** What the sessions table stores instead of the cookie's value. Shared with lib/session.ts so the two never drift. */
export const hashSession = (token: string) => createHash("sha256").update(`gloss-session:${token}`).digest("hex");

/** `"scrypt$N$r$p$salt$hash"`, so the cost can be raised later without invalidating old hashes. */
export function hashPassword(plain: string): string {
  const salt = randomBytes(16);
  const hash = scryptSync(plain.normalize("NFKC"), salt, SCRYPT.keylen, SCRYPT);
  return `scrypt$${SCRYPT.N}$${SCRYPT.r}$${SCRYPT.p}$${enc(salt)}$${enc(hash)}`;
}

/** Constant-time when it matters: a wrong hash must take the same time as a wrong password. */
export function verifyPassword(plain: string, stored: string): boolean {
  const parts = stored.split("$");
  if (parts.length !== 6 || parts[0] !== "scrypt") return false;
  const [, N, r, p, salt, hash] = parts;
  try {
    const expected = Buffer.from(hash, "base64url");
    const got = scryptSync(plain.normalize("NFKC"), Buffer.from(salt, "base64url"), expected.length, {
      N: Number(N), r: Number(r), p: Number(p),
    });
    return expected.length === got.length && timingSafeEqual(expected, got);
  } catch {
    return false;
  }
}

/* ---------- users ---------- */

const newId = (prefix: string) => `${prefix}_${randomBytes(16).toString("base64url")}`;

export async function createUser(email: string, password: string, name?: string): Promise<{ id: string } | { error: string }> {
  const key = email.trim().toLowerCase();
  if (!/^[^@\s]+@[^@\s]+\.[^@\s]+$/.test(key)) return { error: "That email does not look right." };
  if (password.length < 10) return { error: "Use at least 10 characters." };

  const id = newId("usr");
  try {
    await db().query(
      "insert into users (id, email, name, hash) values ($1, $2, $3, $4)",
      [id, key, name?.trim().slice(0, 80) || null, hashPassword(password)]
    );
  } catch {
    return { error: "That email is already registered." }; // unique violation
  }
  return { id };
}

/** A new session row; returns the cookie value, which the caller must not log. */
export async function startSession(userId: string, userAgent?: string): Promise<string> {
  const id = newId("ses");
  const token = randomBytes(32).toString("base64url");
  await db().query(
    "insert into sessions (id, user_id, token_hash, expires_at, user_agent) values ($1, $2, $3, now() + interval '30 days', $4)",
    [id, userId, hashSession(token), userAgent?.slice(0, 200) ?? null]
  );
  return token;
}

export async function endSession(sessionId: string) {
  await db().query("delete from sessions where id = $1", [sessionId]).catch(() => {});
}

/** Expired sessions are swept opportunistically; nobody runs a cron for this. */
export async function sweepSessions() {
  await db().query("delete from sessions where expires_at <= now()").catch(() => {});
}
```

### 5.2 新建 `lib/session.ts`

**单一职责分工**：`auth.ts` 负责写（注册、开会话、关会话），`session.ts` 负责读（当前是谁）。两者共用 `COOKIE` 常量和 `hashSession()`，避免两处实现漂移。

```typescript
/**
 * Who is reading, from the session cookie. The only thing the rest of Gloss
 * needs. Returns null when there is no session or it has expired.
 *
 * Server-side only: reads cookies(), which cannot run in the browser.
 */

import { cookies } from "next/headers";
import { db } from "./db";
import { COOKIE, hashSession } from "./auth";

export type Viewer = { id: string; name: string | null; sessionId: string };

export async function currentUser(): Promise<Viewer | null> {
  const token = (await cookies()).get(COOKIE)?.value;
  if (!token) return null;
  const rows = await db().query(
    `update sessions set expires_at = least(expires_at + interval '1 day', now() + interval '30 days')
     where token_hash = $1 and expires_at > now()
     returning id, user_id`,
    [hashSession(token)]
  );
  if (!rows.length) return null;
  const u = await db().query("select name from users where id = $1", [rows[0].user_id]);
  return { id: rows[0].user_id as string, name: (u[0]?.name as string) ?? null, sessionId: rows[0].id as string };
}
```

/**
 * Whether someone is signed in, and who they are. Reads /api/auth/me once on
 * mount and keeps the answer, so every component agrees without each one
 * asking again.

export function useViewer(): { loaded: boolean; id: string | null; name: string | null } {

  return v;

## 八、新建API 路由

### 8.1 `app/api/auth/route.ts`

```typescript
import { cookies } from "next/headers";
import { COOKIE, createUser, hashPassword, startSession, sweepSessions, verifyPassword } from "@/lib/auth";
import { db } from "@/lib/db";
import { allow, clientId } from "@/lib/ratelimit";

export const runtime = "nodejs";

/** Sign in or create an account. One route, because one form posts to it either way. */
export async function POST(req: Request) {
  // Brute-force guard: 10 tries a minute per address.
  if (!allow(`auth:${clientId(req)}`, 10, 60_000)) {
    return Response.json({ error: "Too many tries. Wait a minute." }, { status: 429 });
  }
  sweepSessions(); // fire and forget; failures are ignored on purpose

  const body = (await req.json().catch(() => ({}))) as { mode?: string; email?: string; password?: string; name?: string };
  const email = String(body.email ?? "");
  const password = String(body.password ?? "");
  const mode = body.mode === "up" ? "up" : "in";

  let userId: string;
  if (mode === "up") {
    const made = await createUser(email, password, body.name);
    if ("error" in made) return Response.json(made, { status: 400 });
    userId = made.id;
  } else {
    const u = await db().query("select id, hash from users where email = $1", [email.trim().toLowerCase()]);
    // Hash a throwaway when the account is missing, so "no such email" and
    // "wrong password" take the same time and cannot be told apart. Both
    // branches below must call hashPassword exactly once.
    if (!u.length) {
      hashPassword(password);
      return Response.json({ error: "That email and password do not match." }, { status: 401 });
    }
    if (!verifyPassword(password, u[0].hash as string)) {
      return Response.json({ error: "That email and password do not match." }, { status: 401 });
    }
    userId = u[0].id as string;
  }

  const token = await startSession(userId, req.headers.get("user-agent") ?? undefined);
  (await cookies()).set(COOKIE, token, {
    httpOnly: true, sameSite: "lax", secure: process.env.NODE_ENV === "production",
    path: "/", maxAge: 30 * 24 * 60 * 60,
  });
  return Response.json({ ok: true, returnTo: "/library" });
}
```

⚠️ **注意那段"假哈希"**：即使用户不存在也要跑一次 `hashPassword`，否则"邮箱不存在"会比"密码错误"返回快得多，攻击者能据此枚举有效邮箱。

### 9.2 ⚠️ 免费层的硬限制：必须验证域名

Resend 免费层**只能发到自己的注册邮箱**，除非验证自己的发信域名。要从 `you@yourdomain.com` 发信，必须：

1. 有一个域名
2. 在 Resend 添加域名

// app/api/cron/daily-review/route.ts

## 十、部署

### ⚠️ 先说不能做什么

**这个项目不能打包成 Electron / Tauri 单机 exe。**

实测确认：
- **13 个 API 路由**依赖 Node 服务端（`runtime = "nodejs"`）：AI 问答、PDF 解析、封面生成、导入、同步、MCP
- 用到 `node:crypto`、`node:dns/promises`、`node:net`
- `public/library/` 下有 WASM 文件
- `node_modules` 总计 480M

强行打包会把 480M 依赖塞进安装包，而且 AI 与 PDF 功能全部失效。**正确做法是部署成服务器，用浏览器访问。**

### 10.1 阶段一：局域网自托管（零成本，先验证）

**第1 步：改配置**
```typescript
// next.config.ts
const nextConfig: NextConfig = {
  output: "standalone",   // ← 新增
  devIndicators: false,
  serverExternalPackages: ["linkedom"],
  // ... 其余不变
};
```

**第 2 步：构建**
```bash
npm run build
```

⚠️ **注意**：`output: "standalone"` **不会**自动拷贝 `public/` 和 `.next/static/`，要手动：
```bash
cp -r public .next/standalone/
cp -r .next/static .next/standalone/.next/
```

**第 3 步：运行**
```bash
PORT=3200 HOSTNAME=0.0.0.0 node .next/standalone/server.js
```

⚠️ **Windows 注意**：`standalone` 在 Windows 上可能因为符号链接权限问题回退到junction，且**junction 不可迁移**。构建产物要留在原目录用，不要复制到别处。

**第 4 步：同网访问**
手机连同一 WiFi，访问 `http://电脑IP:3200`。

### 10.2 阶段二：公网部署

| 方式 | 成本 | 说明 |
|---|---|---|
| **Vercel** | 免费层 | `git push` 即上线。注意 Hobby 层 cron 每天限一次 |
| Docker 自建 | 服务器费用 | `standalone` 产物 + Dockerfile，镜像约 200MB |
| 国内云服务器 | 几元/月 | 需域名 ICP 备案 |

⚠️ **环境变量注意**：`NEXT_PUBLIC_*` 会在**构建时内联**，运行时改无效。部署前必须配好，服务端变量则可在运行时设。

### 10.3 局域网部署的已知限制

| 问题 | 原因 | 绕法 |
|---|---|---|
| 休眠时访问不到 | 电脑睡了 | 电源设置改成不自动睡眠 |
| 手机无法跨网访问 | 无公网入口 | 阶段二解决 |
| Cookie `secure` 标志 | HTTP 下不能设 | 代码里已按 `NODE_ENV` 判断 |

## 十二、风险与注意

### 🔴 迁移问题（当前无风险，将来要处理）

现有8 张表里的数据是用 Clerk 的 `user_id` 写的。换成自建 id 后，**旧数据的 `user_id` 对不上**。

**好消息**：目前 `.env.local` 里没有 `DATABASE_URL`，Neon 上是空的，**没有需要迁移的数据**。

**将来如果要迁移**：在 `lib/session.ts` 里加一层映射——
```typescript
// Clerk ids looked like "user_2abc..."; ours look like "usr_xxx".
// If old rows must keep working, map the old id onto the new user here.
```
更简单的做法是改 `user_id` 列的值，或者建一张 `old_id_map` 表。

### ⚠️ 安全要点清单

自建认证最容易漏的几处，本方案都覆盖了：

| 要点 | 本方案做法 |
|---|---|
| 密码明文 | 从不存储，只存 scrypt 哈希 |
| 时序攻击 | `timingSafeEqual` + 假哈希，让失败路径耗时相同 |
| 暴力破解 | `lib/ratelimit.ts` 的 `allow()`，10 次/分钟 |
| 会话泄漏 | Cookie 只存 id，数据库存哈希 |
| XSS 窃取会话 | Cookie 设 `httpOnly` |
| CSRF | `sameSite: "lax"` + 只接受 POST JSON |
| SQL 注入 | 全部走参数化查询（`$1` 占位符） |
| 枚举邮箱 | 失败时统一返回同一句话、同一耗时 |

### ⚠️ 单人使用的可以省掉

这些不做也没关系，但要知道是**选择**不是**遗漏**：

- 邮箱验证（单人使用，忘了密码改库即可）
- 忘记密码邮件
- 双因素认证
- 登录失败锁定
- 多设备会话管理界面

| 项 | 实测值 |
|---|---|
| scrypt 哈希耗时（N=16384） | **60ms**（首次）/ **47ms**（平均） |
| 正确密码验证 | 通过 |
| 错误密码拒绝 | 通过 |

⚠️ **写作过程中发现并修正的缺陷**：初版把"假哈希"写成
`if (!u.length || !verifyPassword(...)) { hashPassword(password); ... }`。
短路求值导致邮箱存在且密码正确时**跳过**假哈希（但那条路径本来就返回成功，无害），
真正的缺陷是邮箱存在但密码错误时 `verifyPassword` 已返回 false，
而邮箱不存在时才跑假哈希 —— 实测 47ms vs **0ms**，可被用于枚举邮箱。
已改为两个失败分支各自恰好跑一次哈希，实测均为 47ms。**
